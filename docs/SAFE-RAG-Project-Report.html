1. What This Project Does

SAFE-RAG takes two pieces of text — a source context (e.g. a document, a database record, retrieved passages) and an LLM-generated answer that claims to be based on that context — and checks whether the answer is actually supported by the context.

It does this the way a fact-checker would: it splits the answer into individual factual claims (roughly one per sentence), and for each claim decides one of three verdicts:

VerdictMeaning
SupportedThe context confirms this claim.
ContradictedThe context directly disagrees with this claim (a hallucination).
AbstainThe context has no information to confirm or deny this claim (e.g. a forecast, an opinion).

Each claim also gets:

  • A risk score (0–100): how likely the claim is a hallucination.
  • An error type: numerical_mismatch, temporal_mismatch, entity_mismatch, formatting_mismatch, unverifiable, or none.
  • Evidence: a quote/paraphrase from the context justifying the score.

The project has two halves: a real backend REST API that does this classification work, and a frontend dashboard (already scaffolded before this work began) that was previously wired to fake setTimeout mock data. All six frontend pages now call the real backend.

The two halves are separate processes talking over plain HTTP + JSON, secured with a Bearer API key and CORS-restricted to the frontend's origin. This mirrors how a real product would be built: a thin client and an independently deployable, independently testable API service.

Persistence

There is no database. Three JSON files under backend/data/ act as tiny collections:

FileHolds
api_keys.jsonIssued API keys (id, secret, label, revoked flag, last-used time)
settings.jsonThe current risk-threshold configuration (lower/upper bound)
history.jsonAn append-only log of every verification run — this is what powers Analytics/Dashboard with real numbers

This is a deliberate simplification for a course project: fully inspectable, zero setup, easy to explain — not meant to be how a production system would store this data (see Section 9).

3. How a Request Actually Flows Through the System

Walking through one concrete example end to end — this is the best thing to narrate live in the demo.

Input

context: "Q3 revenue was $45M, reported on March 3, 2024 by CEO Jane Smith."
answer:  "The company revenue grew to $50M in Q3. The new product launched
          in 2025. CEO John Doe announced record margins next year."

Step-by-step

  1. Claim decomposition (backend/app/services/claims.py) splits the answer on sentence boundaries into 3 claims.
  2. Per-claim classification (backend/app/services/verifier.py) sends each claim + the context to Gemini (gemini_client.py) asking for a strict JSON verdict: {risk_score, error_type, evidence}. If Gemini is unavailable or errors, the deterministic rule-based scorer (rules.py) takes over automatically.
  3. Threshold lookup: the current lower_bound/upper_bound settings are read from settings.json. A risk score below the lower bound → Supported; above the upper bound → Contradicted; in between → Abstain.
  4. Result assembly: claims are packaged into the API response and appended to history.json for analytics.

Actual output (captured from a real run of this backend)

{
  "claims": [
    {
      "text": "The company revenue grew to $50M in Q3.",
      "verdict": "Contradicted",
      "risk_score": 88.0,
      "error_type": "numerical_mismatch",
      "evidence": "Context contains different figures: 3, 45."
    },
    {
      "text": "The new product launched in 2025.",
      "verdict": "Contradicted",
      "risk_score": 82.0,
      "error_type": "temporal_mismatch",
      "evidence": "Context references different dates: 2024."
    },
    {
      "text": "CEO John Doe announced record margins next year.",
      "verdict": "Abstain",
      "risk_score": 55.0,
      "error_type": "unverifiable",
      "evidence": null
    }
  ],
  "hallucination_rate": 100.0,
  "engine": "rule_based_fallback"
}
Good demo moment: point out that the numeric mismatch ($50M vs $45M) and the date mismatch (2025 vs 2024) were correctly separated into different error_type categories, and the unverifiable forecast about "next year" correctly abstained instead of being falsely marked right or wrong.

4. Backend — File by File

All under backend/app/.

Entry point

FileRole
main.pyCreates the FastAPI app, adds CORS middleware, registers all routers, runs ensure_default_key() on startup so a working API key always exists.
config.pyLoads .env: Gemini key/model, allowed CORS origins, whether auth is required, history size limit.
schemas.pyEvery Pydantic request/response model (VerifyRequest, Claim, BatchResponse, ThresholdSettings, ApiKeyPublic, analytics models, etc.) — this is the API's data contract.
store.pyTiny generic JSON-file read/write helper with a thread lock, used by every service below.
security.pyAPI key lifecycle: create, list, roll (rotate secret), revoke, and the require_api_key dependency that every protected route depends on.

Services (app/services/) — the actual verification logic

FileRole
claims.pySplits an answer string into individual claim sentences.
gemini_client.pyBuilds the classification prompt and calls the Gemini API, asking for strict JSON. Returns None on any failure so the caller can fall back.
rules.pyDeterministic backup classifier: compares numbers, 4-digit years, and capitalized entities between claim and context using regex. No LLM call, no network — always available.
verifier.pyOrchestrator: decomposes the answer, tries Gemini per claim, falls back to rules, converts each risk score into a verdict using the current thresholds. This is the file that ties everything together.
settings_service.pyGet/save the threshold configuration.
history.pyAppends every verification run to the history log and reads it back for analytics.

Routers (app/routers/) — the HTTP surface

FileEndpoints
verify.pyPOST /v1/verify — single context/answer pair
batch.pyPOST /v1/batch — a list of pairs, returns per-row + aggregate summary
settings_router.pyGET/PUT /v1/settings
api_keys.pyGET/POST /v1/api-keys, /roll, /revoke, /bootstrap
analytics.pyGET /v1/analytics/summary, /timeseries, /models — all computed live from history.json

6. The Swagger Docs Page (/docs)

FastAPI auto-generates this page from the Pydantic schemas and route definitions in the code — nothing was hand-written for it. Open http://127.0.0.1:8000/docs while the backend is running.

What's on it

  • Every endpoint, grouped by tag (verify, batch, settings, api-keys, analytics).
  • The exact request body schema and response schema for each — generated straight from schemas.py, so it can never drift out of sync with the real API.
  • A "Try it out" button on every endpoint that sends a real request to your running backend and shows the real response, right in the browser — no Postman or curl needed.

What to do with it during the presentation

  1. Expand POST /v1/verify, click Try it out.
  2. Paste a context/answer pair into the example body and click Execute.
  3. Scroll down and show the real JSON response with verdicts, risk scores, and error types.
Why this matters for an API course: it proves the system is a genuine, independently usable REST API — not logic baked into the frontend. Anyone (a mobile app, another service, a grading script) could call this API directly, with no browser UI involved at all.
One thing to know: /v1/verify requires an Authorization: Bearer <key> header. Grab a working key first from POST /v1/api-keys/bootstrap (no auth needed) or from the Developer API page in the frontend, then paste it into the padlock/Authorize button at the top of the Swagger page before calling protected endpoints.

7. How to Run the Project

Terminal 1 — backend

cd backend
.venv\Scripts\activate
uvicorn app.main:app --reload --port 8000

Ready when you see Application startup complete.  Verify: http://127.0.0.1:8000/v1/health should return {"status":"ok"}.

Terminal 2 — frontend

npm run dev

Open http://localhost:3000.

Works with zero configuration — no Gemini key needed. Without one, every claim is scored by the rule-based fallback automatically. To use real Gemini classification, get a free key at aistudio.google.com/apikey and paste it into backend/.env as GEMINI_API_KEY, then restart the backend terminal.

9. Design Decisions & Known Limitations

DecisionWhyWhat a production system would do instead
Sentence-level claim splitting (regex)Simple, fast, good enough for short LLM answersLLM-based atomic sub-claim decomposition
JSON files instead of a databaseZero setup, fully inspectable for a demoPostgres/SQLite with proper concurrency
Rule-based fallback (regex number/date/entity overlap)Keeps the demo working with no API key, no internet, or a rate-limited keyA real trained NLI/entailment model as the fallback, not just the safety net
Plaintext API keys in a JSON fileEasy to reason about and demoHashed keys, a real auth/session system for the key-management endpoints
One Gemini call per claimSimple, clear per-claim evidenceBatched/parallel calls for large-scale batch jobs

10. Relationship to the Reference Paper

The reference repository (LeNguyenAnhKhoa/Hallucination-Detection) is the code for "A.M.P at SciHal2025: Automated Hallucination Detection in Scientific Content via LLMs and Prompt Engineering" (ACL 2025 SDP Workshop) — 4th place in Subtask 1 and 2nd place in Subtask 2 of the SciHal2025 shared task.

It is not a REST API — it's a set of research scripts that call the Gemini/OpenAI APIs with few-shot prompts to classify a claim vs. a reference as Entailment, Contradiction, or Unverifiable.

Reference paper conceptThis project's equivalent
EntailmentSupported
ContradictionContradicted
UnverifiableAbstain
Few-shot prompt asking for a labelgemini_client.py's structured JSON prompt asking for a risk score + error type

What this project adds on top of that idea: a full serving layer (FastAPI + routing + auth), a threshold-based verdict system instead of the LLM deciding the label directly, a rule-based fallback for resilience, persistence, and a connected frontend — none of which exist in the reference repo.

11. Anticipated Questions & Answers

Q: Why does the LLM output a risk score instead of the verdict directly?

A: So the Supported/Contradicted/Abstain cutoffs are configurable at runtime (via Settings) without needing to change the prompt or re-call the model — the same score can be re-classified under different thresholds instantly.

Q: What happens with no internet / no API key?

A: gemini_client.py returns None on any failure, and verifier.py falls back to rules.py automatically per-claim — the API never errors out because of the LLM being unavailable.

Q: How is this secured?

A: Bearer API-key auth on every verification/analytics/settings endpoint, CORS restricted to the frontend's origin only, keys can be rotated or revoked. Key-management endpoints themselves are intentionally open (like a dashboard using session auth) — documented as a simplification in Section 9.

Q: Does it scale?

A: Not as-is — JSON-file storage assumes a single process. The architecture (stateless FastAPI routes, a swappable classification service) would scale by swapping the JSON store for a real database; the API contract wouldn't need to change.

Q: How accurate is the rule-based fallback vs. the LLM?

A: The fallback is intentionally crude (regex overlap) — a safety net for demo resilience, not a competitor to the LLM path. The engine field in every response reports which one was actually used, so this is fully transparent.
